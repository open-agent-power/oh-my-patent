# 申请文件版面规范

本文件记录 `oh_my_patent` 所依据的法规要求，以及每项实现决策的理由。
改动 `spec.py` 或 `oxml.py` 前应先读这里。

## 一、纸张与版面

### 规定

- 纸张：A4（210mm × 297mm），纵向
- 页边距：**上 25mm / 左 25mm / 右 15mm / 下 15mm**
- 字高：0.28cm ~ 0.5cm
- 行距：不小于 0.28cm

### 实现

`spec.py` 的 `MARGIN_*` 与 `oxml.configure_section()`。

单位换算：1 毫米 = 56.6929 twips。

| 边距 | 毫米 | twips |
| --- | --- | --- |
| 上 | 25 | 1417 |
| 左 | 25 | 1417 |
| 右 | 15 | 850 |
| 下 | 15 | 850 |

### 关于字体大小

指南只规定**范围**（0.28~0.5cm）而非唯一值。正文取 **12pt（小四）**，
字高约 0.42cm，落在范围中部，是实务中最通用的取值。

字号写法：OOXML 用**半磅**，12pt 写作 `w:sz w:val="24"`。

## 二、字体

### 规定

允许使用的汉字字体：**宋体、仿宋、黑体**。

### 实现

`spec.py` 的 `Font` 枚举与 `RenderOptions.font`。

西文必须**单独声明**。OOXML 的 `w:rFonts` 区分 `w:ascii` / `w:hAnsi`
（西文）与 `w:eastAsia`（东亚文字）：

| 汉字字体 | 配对西文字体 |
| --- | --- |
| 宋体 | Times New Roman |
| 仿宋 | Times New Roman |
| 黑体 | Arial |

不显式指定西文字体时，WPS 与 Office 会各自套用不同的回退字体，
同一段文字里的数字和英文宽度不同，中文文书会整体「串行」。

### `w:hint="eastAsia"` 的必要性

中文标点、全角字符、以及落在中西文模糊区间的字符，依据 `w:hint` 决定用哪套
字体。缺了它，两个软件会对同一段的中文标点各选各的字体，标点宽度不一，
直接导致行尾对齐出现差异。

## 三、说明书结构

### 规定

细则与指南要求说明书文字部分包括五个部分，**按下列顺序**：

```
【技术领域】
【背景技术】
【发明内容】        （实用新型写作「实用新型内容」）
【附图说明】
【具体实施方式】
```

### 各部分要求

**技术领域**：写明发明或实用新型所属或者直接应用的技术领域。

**背景技术**：写明对发明或实用新型的理解、检索、审查有用的背景技术；
引证反映这些背景技术的文件。**并指出现有技术存在的问题与缺陷。**

**发明内容**：写明
1. 要解决的技术问题
2. 解决其技术问题采用的技术方案（应与独立权利要求一致，可写得更完整）
3. 有益效果

**附图说明**：说明书有附图的，逐幅说明。写法：`图1为……示意图。`

**具体实施方式**：详细描述实现发明或实用新型的优选方式；有附图的应**对照附图**。
充分公开的底线是「所属技术领域的技术人员能够实现」。

### 实现

`spec.py` 的 `SECTION_ORDER` / `SECTION_TITLES`，渲染见
`render/docx.py` 的 `_description_blocks()`。

章节标题写作 `【技术领域】` 这种加方括号的形式，符合公开文本惯例。

`--subsection-style` 控制「发明内容」下三级小标题的处理：

| 取值 | 效果 | 适用场景 |
| --- | --- | --- |
| `inline`（默认） | 小标题并入段落作加粗引导词，如「**技术方案：**本发明提供……」 | 最接近代理师正式稿 |
| `keep` | 保留为独立加粗段落 | 内部审阅，需要清晰结构 |
| `flatten` | 丢弃小标题，只留正文 | 最「干净」的正式稿 |

指南并未规定发明内容下还能再分小标题，因此默认取最贴近正式稿的 `inline`。

## 四、附图

### 规定

- 几幅附图按「图1，图2，……」**顺序编号**
- **说明书文字部分未提及的附图标记不得在附图中出现；附图中未出现的附图标记
  不得在说明书文字部分中提及**（细则第 21 条）
- 表示同一组成部分的附图标记应当一致
- 附图中除必需的词语外不应含有其他注释
- **实用新型的说明书必须有附图**
- 有附图的申请应当提供一幅**最能说明发明或实用新型技术特征的附图**作为摘要附图
- 附图应能在缩小到 4cm × 6cm 时仍清晰分辨细节

### 实现

- 图号与说明从「附图说明」章节的 `图N为……` 句式提取
- `lint.check_description()` 的 `DESC-005` 检查正文引用的图号是否真实存在
- `DESC-007` 检查实用新型是否有附图
- 摘要附图：显式指定的优先（`abstract: true` 或 alt 文本含「摘要附图」），
  否则取**编号最小**的一幅（不是列表顺序，避免受稿件排列影响）
- 插图自动约束到正文宽度 170mm 与最大高度 200mm 内

## 五、权利要求书

### 规定

**编号**：有几项权利要求的，用**阿拉伯数字顺序编号**。

**构成**：任何一项权利要求都应包含**主题名称**与**技术特征**。

**独立权利要求**（细则第 24 条）包括两部分：
- 前序部分：主题名称 + 与最接近现有技术共有的必要技术特征
- 特征部分：`其特征是……` 或类似用语 + 区别技术特征

**从属权利要求**（细则第 25 条）包括两部分：
- 引用部分：引用的权利要求编号及主题名称
- 限定部分：附加技术特征

**引用规则**：从属权利要求**只能引用在前的权利要求**。引用两项以上权利要求的
多项从属权利要求，只能以**择一方式**引用，且不得作为另一项多项从属权利要求的
基础。

**用语限制**：
- 不得使用「如说明书……部分所述」「如图……所示」（除绝对必要外）
- 不得有**插图**（化学式、数学式可以）
- 技术特征可引用附图标记，放在括号内；**附图标记不得解释为对权利要求的限制**
- 使用的科技术语应与说明书一致

**独立权利要求的数量**：细则写「一项发明或者实用新型应当只有一个独立权利要求」，
但国知局官方答复与最高人民法院的答复均确认：**符合单一性时可以有两项以上**，
写在最前面的为第一独立权利要求，其余为并列独立权利要求。

### 允许的并列组合

《审查指南》第二部分第六章 2.2.1 列出六种：

1. 不能包括在一项权利要求内的两项以上产品或者方法的**同类**独立权利要求
2. 产品和**专用于制造该产品**的方法的独立权利要求
3. 产品和该产品的用途的独立权利要求
4. 产品、专用于制造该产品的方法和该产品的用途的独立权利要求
5. 产品、专用于制造该产品的方法和为实施该方法而专门设计的设备的独立权利要求
6. **方法和为实施该方法而专门设计的设备**的独立权利要求

判断单一性的标准是：权利要求中是否包含**使它们在技术上相互关联的一个或者
多个相同或相应的特定技术特征**。所谓特定技术特征，是指对现有技术作出贡献的
技术特征。

### 实现

- `schema.parse_claims_block()` 分段与独立/从属判定
- `schema._expand_references()` 展开「权利要求1至3中任一项」这类引用
- `lint.check_claims()` 的检查项：

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `CLAIM-001` | ERROR | 缺少权利要求书 |
| `CLAIM-002` | ERROR | 编号不连续 |
| `CLAIM-003` | ERROR | 没有独立权利要求 |
| `CLAIM-004` | WARNING | 多项独立权利要求，提示复核单一性 |
| `CLAIM-005` | WARNING | 独权中没有「其特征在于」 |
| `CLAIM-006` | WARNING | 从权未写明引用的权利要求编号 |
| `CLAIM-007` | ERROR | 引用了在本项之后或就是本项的权利要求 |
| `CLAIM-008` | WARNING | 含含义不确定的用语 |
| `CLAIM-009` | INFO | 单项超过 800 字 |
| `CLAIM-010` | ERROR | 第一项不是独立权利要求 |
| `CLAIM-011` | WARNING | 引用说明书或附图 |
| `CLAIM-012` | ERROR | 含插图 |
| `CLAIM-013` | ERROR | **实用新型**中出现方法类独立权利要求 |

## 六、说明书摘要

### 规定

- 写明所公开内容的概要：**名称、所属技术领域、要解决的技术问题、技术方案的
  要点、主要用途**
- 可以包含最能说明发明的化学式
- **文字部分不得超过 300 个字**
- **不得使用商业性宣传用语**
- 有附图的申请应当提供一幅最能说明技术特征的附图

### 实现

`spec.ABSTRACT_MAX_CHARS = 300`。字数统计**忽略空白**，汉字与标点各计一字。

统计口径说明：字数统计在不同软件、不同历史时期的口径并不统一（有的把
`w:p` 段落符也算进去）。这里采用最保守的口径——精确统计可见字符，
不含任何格式符。300 字是硬上限，本地统计不超就不会超。

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `ABS-001` | ERROR | 缺少摘要 |
| `ABS-002` | ERROR | 超过 300 字 |
| `ABS-003` | WARNING | 已逼近 300 字（超过 280） |
| `ABS-004` | WARNING | 含商业性宣传用语 |
| `ABS-005` | INFO | 通篇无句读 |

## 七、外观设计

### 规定

外观设计专利申请文件包括：请求书、**图片或照片**、**简要说明**。

**没有权利要求书，没有说明书。** 保护范围以图片或照片为准。

简要说明应当写明：
1. 产品的名称
2. 产品的用途
3. **设计要点**
4. 最能表明设计要点的图片或照片
5. 必要时：省略视图的情况、是否请求保护色彩

**图片要求**：一般提交**六面视图**（主视图、后视图、左视图、右视图、俯视图、
仰视图）；必要时提交立体图、剖视图、放大图等。

### 实现

- `schema.DesignBrief` 模型
- `render/docx.py` 的 `_render_design_brief()`，按法定顺序编号输出五个条目
- `lint.check_design()`：

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `DES-001` | ERROR | 简要说明缺「用途」 |
| `DES-002` | ERROR | 简要说明缺「设计要点」 |
| `DES-003` | ERROR | 未指定最能表明设计要点的图片 |
| `DES-004` | ERROR | 没有登记任何图片 |
| `DES-005` | WARNING | 视图没有实际的图片文件路径（生成时会留空） |

> **命名沿革**：`DES-001`~`DES-003` 早先是 `DES-USAGE` / `DES-POINTS` /
> `DES-BEST_VIEW` 这样的词码，与全项目 `前缀-三位数字` 的写法不一致，已统一。
> 该组原先**零测试覆盖**，本次一并补上（`tests/test_lint_design.py`）。

## 八、发明名称

### 规定

- 应清楚、简要地反映要求保护的技术方案的**主题和类型**
- 与请求书中的名称**一致**
- 一般不超过 **25 字**，特殊情况不超过 **40 字**
- 不得含有人名、地名、商标、型号、商品名称
- 不得含有非技术用语
- **不得使用标点**（必要的括号除外）

### 实现

`spec.TITLE_FORBIDDEN_WORDS` 收录确定违规的词：`专利`、`新型`、`改进`、
`及其他`、`等类似`。

**注意「技术」不是禁用词。** 「一种基于边缘计算的数据采集**技术**」完全合法，
把它列进禁用词表会造成大量误报。同理「方法」「装置」「系统」都是合法用词。

`spec.TITLE_SOFT_WORDS` 收录含糊表述（`等`、`系列`、`各种`、`一类`），
报 INFO 而非 ERROR。

## 九、WPS 与 Office 兼容性

这一节不是法规要求，而是工程约束。详细背景见 `README.md` 的
「WPS / Office 双适配」一节，此处只列实现清单。

| 措施 | 位置 | 解决的问题 |
| --- | --- | --- |
| 去主题化 | `oxml.de_theme_fonts()` | 主题中 `<a:ea typeface=""/>` 为空，中文字体解析结果由各软件决定 |
| 处理 `stylesWithEffects.xml` | 同上，走 `de_theme_blob()` | 该文件是 `styles.xml` 的完整副本，只清一处会整份漏掉 |
| 每个 run 写全四项字体 + `hint` | `oxml.set_run_font()` | 中西文回退差异 |
| 补 `docDefaults` 的 `w:eastAsia` | `oxml._patch_doc_defaults()` | 中文落到哪个字体 |
| 写死 `compatibilityMode=15` | `oxml._patch_settings()` | WPS 可能按 Word 2003 模式排版 |
| 关闭文档网格 | `oxml.configure_section()` | 行距被吸附到网格，两软件吸附算法不同 |
| 不用 `w:numPr` 自动编号 | `render/docx.py` | WPS 的 `numbering.xml` 实现差异导致编号错位 |
| 首行缩进用字符单位 | `oxml.set_paragraph_format()` | 磅值缩进不随字号变化 |
| 严守 schema 元素顺序 | `oxml.insert_ordered()` | 顺序错在 WPS 能开、Office 报损坏 |
| 分页用 `w:pageBreakBefore` | `oxml.set_page_break_before()` | 插入空段落会在 WPS 里被撑成整页空白 |

### 为什么必须做 schema 顺序

ECMA-376 规定 `w:rPr` 子元素必须按特定顺序出现（例如 `w:rFonts` → `w:b` →
`w:sz` → `w:lang`）。这个顺序错了：

- **WPS**：宽容处理，照常打开
- **MS Office**：可能直接报「文件已损坏，是否修复」

这个不对称极其隐蔽——在 WPS 里验证通过的代码，可能在 Office 里全面崩盘。
因此 `tests/test_render.py` 里有专门的断言守住元素顺序，
`insert_ordered()` 必须用 `qn()` 归一化标签后再比较（直接比较 `w:rFonts`
与 Clark 记法 `{http://...}rFonts` 永远不相等，函数会静默退化成 `append()`）。

## 十、AI / 算法类发明的专有要求

**依据**：《专利审查指南》第二部分第九章第 6 章，经《国家知识产权局关于修改
〈专利审查指南〉的决定》（**局令第 84 号**）修改，2025-11-10 公布，
**自 2026-01-01 起施行**。

> ⚠️ **时效提示**：本项目的判据以 2026-01-01 施行的版本为准。网络上大量
> 资料仍在引用 2021 年版，涉及 AI 的部分已不完整。

本次修改对 AI 相关申请加了两道实质门槛，都落在说明书上。

### 10.1 充分公开（第 6.3.1 节 → 专利法第 26 条第 3 款）

指南原文规定，包含算法特征或商业规则和方法特征的发明专利申请，其说明书
应当清楚、完整地描述发明为解决其技术问题所采用的解决方案。解决方案在包含
技术特征的基础上，**可以进一步包含与技术特征功能上彼此相互支持、存在相互
作用关系的算法特征**。

指南把 AI 相关申请分成两种情形，要求各有侧重：

| 情形 | 说明书一般需要记载 |
| --- | --- |
| 涉及**AI 模型的构建或者训练** | 模型必要的**模块、层级或者连接关系**；训练必需的**具体步骤、参数**等 |
| 涉及**在具体领域或者场景中应用** AI 模型或算法 | 模型或算法**如何与具体场景结合**；**输入、输出数据如何设置**以表明其内在关联关系 |

落脚点都是同一句：使所属技术领域的技术人员按照说明书记载的内容**能够实现**
该解决方案。

指南新增了审查示例（第 6.3.3 节）：

- **例 20（公开充分）**：人脸特征生成方法。说明书详细描述了模型层级结构、
  各网络间的信息共享方式。虽然未指明空间变换网络在第一网络中的具体插入层
  位置，但该位置不影响其功能，且卷积网络与空间变换网络均为公知算法，
  本领域技术人员能够构建——**认定充分公开**。
- **例 21（公开不充分）**：基于生物信息预测癌症的方法。说明书未记载究竟
  哪些具体血液检测指标与肿瘤预测相关、是否使用全部指标或赋予不同权重，
  也未证明人脸特征与恶性肿瘤存在明确关联——**认定公开不充分**。

例 20 说明：结构、步骤交代清楚后，个别模块位置未精确限定仍可接受。
例 21 说明：含糊的「可采用多种指标／算法」不足以支撑。

**实现**：`lint_ai.check_ai_disclosure()`，检查项 AI-001 ~ AI-006。

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `AI-001` | ERROR | 权利要求出现模型／算法特征，说明书未描述（只有领域或任务层面表述） |
| `AI-002` | ERROR | 涉及模型构建／训练，但未记载模块、层级或连接关系 |
| `AI-003` | WARNING | 提到「训练」，但未记载训练步骤或参数 |
| `AI-004` | WARNING | 未见输入、输出数据的描述 |
| `AI-005` | WARNING | 出现黑箱式表述（「具体算法不作限定」等） |
| `AI-006` | WARNING | 偏重效果承诺而无技术手段（「采用神经网络提高……」） |

### 10.2 伦理合规（新增第 6.1.1 节 → 专利法第 5 条第 1 款）

指南新增规定：对于申请文件中记载的**数据采集、标签管理、规则设置、推荐决策**
等内容，如果违反法律、社会公德或者妨害公共利益，则依据专利法第 5 条第 1 款
不予授予专利权。

指南新增审查示例中的两个反例：

- 在顾客**未察觉**的情况下采集面部与身份信息做精准营销 → 数据获取不合法
- 以行人的**性别、年龄**决定碰撞保护对象 → 违背社会公德。指南的表述是
  「人的生命具有同等价值和尊严」

**实现**：`lint_ai.check_ai_ethics()`。

| 代码 | 级别 | 检查内容 |
| --- | --- | --- |
| `ETH-001` | ERROR | 以人身属性作决策依据，且决策影响人身权益或社会资源分配 |
| `ETH-003` | WARNING | 以人身属性作处理逻辑依据，提示评估合规性 |
| `ETH-002` | WARNING | 处理敏感个人信息但未见合法性声明 |

**为什么分 ERROR 与 WARNING 两档**：以年龄确定给药剂量这类医疗方案完全正当，
静态检查看不出语境差别。只有决策影响人身权益或资源分配时（指南案例 10 的
情形）才判 `ERROR`，一般性的属性决策降为 `WARNING` 交使用者判断。

### 10.3 算法特征与技术特征的关系（第 6.2 节，例 18／19）

指南新增明确规定：涉及人工智能模型的技术方案，应当对**深度学习、模型构建
或者训练过程**做出改进，算法特征与技术特征应当**相互支持、相互作用**，
才有可能满足创造性要求。

同时第 6.4 节明确：**权利要求中没有对技术问题的解决作出贡献的技术特征，
通常不会给发明带来创造性**。这条修改间接表明，试图通过堆砌无贡献特征来获得
授权将变得更难。

这两条属于**实质判断**，静态检查做不了。本项目不设对应检查项，由使用者
自行论证。

## 十一、非正常申请的合规边界

**依据**：《规范申请专利行为的规定》（**国家知识产权局令第 77 号**），
2023-12-21 公布，**自 2024-01-20 起施行**。

> ⚠️ **引用更正**：网络上大量资料（包括若干专利 Agent 的说明文档）仍在引用
> 《关于规范申请专利行为的办法》（**国家知识产权局公告第 411 号**，2021 年）。
> 第 77 号令施行后，411 号公告已不再是现行有效文本。**引用应以第 77 号令为准。**

与自动化撰写工具直接相关的四种情形（第 77 号令第三条）：

| 项 | 情形 |
| --- | --- |
| (一) | 多件专利申请的发明创造内容明显相同，或者实质上由不同特征、要素**简单组合**形成的 |
| (二) | 存在**编造、伪造、变造**发明创造内容、实验数据或技术效果，或者抄袭、简单替换、拼凑现有技术的 |
| (三) | 发明创造内容**主要为利用计算机技术等随机生成**的 |
| (四) | 明显不符合技术改进、设计常理，或者**变劣、堆砌、非必要缩限保护范围**的 |

使用 AI 批量起草申请文件时，(一)(三)(四) 三种情形是最现实的风险。

**本项目的立场**：工具无法判断申请人的真实研发活动，因此

1. **不提供批量生成能力**，也不做「一键产出多件专利」这类功能；
2. 对所有涉及编造的内容一律标 `【待补：具体说明】` 而不是编一个看起来
   合理的值——`lint.check_placeholders()` 会把残留的占位符报为 `ERROR`；
3. 生成物附带的说明中写明第 77 号令的要求，提示由对发明创造实质性特点
   作出创造性贡献的自然人核实内容真实性后提交。

判错的代价比不判更高。

### 关于误报

本项目的检查层有一批术语表驱动的判据，误报风险集中在这里。已经踩过的坑：

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 非贪婪正则在中文里从词中间起匹配 | 「权利要求1至5」被拆出假标记「5」 | 用贪婪匹配取完整汉字串，再看串尾 |
| 任务词当开关 | 「异常检测」让纯机械专利被 AI 规则打扰 | 检查是否执行只看核心词，任务词仅用于生成诊断信息 |
| 输入输出词表过窄 | 「输入图像张量」这种常见写法漏判 | 加一层兜底：同时出现「输入」与「输出」即放过 |

**判断原则**：一条检查只要偶尔胡说，使用者就会连正确的提醒一起不信任。
因此宁可漏报，不可误报——凡是不够确定的，降低级别并附上核查指引，
而不是替审查员下结论。

新增术语表时，**必须**在 `tests/test_lint_ai.py` 里补一条「不误报」的用例，
并确认 `ExamplesTest` 仍然全绿。
