# 03 · 专利点挖掘与融合

> **状态：已实现**（本步无脚本，由你判断；`04` 的查新工具是可选增强）。
> 本文件是**可执行流程**，按它做。

## 什么时候进入这一步

`02` 的扫描摘要已经产出，用户要「看看能申请什么」「挖一挖专利点」「这些材料能写几件」。
用户也可以直接给一段话描述，跳过 `02`。

## 这一步产出的是什么

**候选专利点清单**——不是申请文件，也不是「能不能授权」的结论。

| 你产出 | 你不产出 |
| --- | --- |
| 这个点解决了什么问题、凭什么算区别 | 「这个能授权」 |
| 建议的类型与理由 | 权利要求的最终保护范围 |
| 依据的源文件位置 | 创造性/新颖性的法律判断（那是审查员的职责） |

## 步骤

### 第 1 步：通读扫描摘要，列出**全部**候选

先求全，不求精。把摘要里所有「像技术贡献」的东西都列出来，包括你觉得弱的——
**筛选放在第 2 步**，一开始就筛会漏掉那种「看着平淡、细看有巧思」的点。

### 第 2 步：逐个过价值判定表

| 情况 | 处理 |
| --- | --- |
| 只是常规工程实现（用现成库、按文档接线、改配置） | **不是专利点。** 不要为了凑数硬写 |
| 有取巧的工程细节但无技术贡献（比如纯粹为了兼容某版本而写的绕过代码） | 通常不足以支撑创造性 |
| 解决了别人解决不了的具体问题 | 候选专利点 |
| 多个点属于**同一发明构思** | 合并为一件申请（单一性） |
| 多个点相互独立 | 拆成多件申请，或分案 |

**同一发明构思的判定是这一步最容易出错的地方**：把不相关的点塞进一件申请，
后面会被要求分案；把该合并的拆开，用户要多花申请费。
判断标准是「是否由同一个技术构思统摄」——例如「双阈值滞回控制」和
「基于同一滞回逻辑的异常上报抑制」属同一构思；而「滞回控制」和「外壳防水结构」
是两个独立构思。

### 第 3 步：给每个点做初步的 D1 对照

对每个候选点，写明：

- **D1**（你目前认为最接近的现有技术）：是什么、依据什么这么认为。
  这一步是**初步**的，正式检索在 `04`。
- **区别特征**：本方案与 D1 相比，多了/不同在哪。要具体到技术手段，
  不能写「效果更好」「效率更高」。
- **该区别带来的技术效果**：为什么这个区别是有意义的。

**如果写不出具体的区别特征，这个点就还不够格**——把它降级为「线索」，
写在清单末尾，不要混在正式候选里。

### 第 4 步：命名与类型建议

工作标题的领域对象**必须能在后续写出来**。

- 好：「一种基于双阈值滞回的智能水表用水量控制方法」——对象具体、能落地
- 差：「一种智能控制系统」「一种数据处理模块」——事后只能写成空泛的「系统/模块」

类型建议要说明理由：

| 类型 | 适用 |
| --- | --- |
| 发明 | 方法、算法、工艺、组合物、有构造的产品 |
| 实用新型 | 产品的形状、构造或其结合（**不含方法**，不含无形状的材料） |
| 外观设计 | 产品的形状、图案、色彩及其结合（看外观，不看技术方案） |

**想申请方法类又只想用实用新型的，必须当场指出冲突**——实用新型不保护方法。

## 硬约束

1. **禁止无依据编造。** 可以基于已有事实**适度推演**（技术上的合理外推），
   但必须有技术合理性支撑。凭空发明一个「创新点」比说「没找到」更糟。
2. **不要指定不相干的文献充当 D1。** 没有把握就写「D1 待检索确认」。
3. **不要空喊「创新性强」。** 判断要有可复核的依据。
4. **某个点判定为「不足以支撑」时，不要停笔。** 继续做完其余点，
   并在清单里如实写出你为什么判定它不够格。
5. **挑不出点就如实说挑不出来。** 直接告诉用户「这批材料里的都是常规实现」，
   并说明理由——这比硬凑三个点有价值得多。

```markdown
## 候选一：<工作标题>

- **一句话概括**：
- **解决的具体问题**：
- **D1（初步，待 04 核实）**：
- **区别特征**：
- **区别带来的技术效果**：
- **依赖的源材料**：交底书.docx 第 2 节 / 评审.pptx 第 3 页
- **建议类型**：发明 —— <理由>
- **信息缺口**：<哪些关键细节还不清楚，需要问用户>

## 候选二：……

## 判定为「不足以支撑」的点

| 点 | 为什么不够格 |
| --- | --- |
| 用 pandas 做数据清洗 | 常规工程实现，无技术贡献 |

## 单一性分析

- 候选一与候选二属**同一发明构思**（都由滞回逻辑统摄），建议合并为一件申请。
- 候选三独立，建议单独申请。

## 需要用户确认的事

- 候选一里的采样周期是 5s 还是 10s？材料里两处不一致。
```

## 明确不要做

- **不要跳过 D1 对照直接给结论**——「这个肯定能授权」是你不能做的判断。
- **不要为了凑数把常规实现写成专利点。**
- **不要在信息缺口没问清时就往下走到 `05`。** 带着窟窿写的交底书，
  到 `06` 写权利要求时会爆出来，那时返工成本高得多。
- **不要把「线索」和「候选」混在一起列。** 两者的可信度不同，混在一起
  会让用户以为都同样靠谱。

## 交付

以「**交付后请确认**」收尾：

- 一共几个候选点、分别是什么、建议类型；
- 哪几个判定为不够格、为什么；
- 单一性结论（合并还是拆分）；
- **需要用户确认的信息缺口**（这是最需要他回应的一项）。
