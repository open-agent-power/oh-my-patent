# 05 · 技术交底书

> **状态：已实现**（本步无脚本，由你撰写）。
> 本文件是**可执行流程**，按它做。

## 什么时候进入这一步

`03` 的候选点已经用户确认，现在要把选定的点写成一份能往下走的交底书。

## 交底书与申请文件的区别（不要混为一谈）

| | 交底书 | 申请文件（`06` 的产物） |
| --- | --- | --- |
| 读者 | 用户自己 / 代理师 | 审查员 / 公众 |
| 性质 | 内部材料 | 对外法律文件 |
| 形式 | 自由 | 法定格式 |
| 不确定的地方 | **可以写「这块还没想清楚」** | 一句都不能含糊 |
| 多个方案 | 可以并列 | 需写成有层次的实施例 |

**先交底书、后申请文件的顺序不能省。** 交底书阶段允许含糊，正是为了让用户
在这里把事想清楚，而不是等写到权利要求时才发现有个关键问题没解决——
那时返工要重写整篇。

**因此：不要把交底书写成申请文件。** 交底书里写「这个参数还在调」是正常的，
在申请文件里就是缺陷。

## 步骤

### 第 1 步：确认输入齐全

需要的素材（来自 `02` 的扫描摘要与 `03` 的候选点）：

- 候选点的技术方案（含 D1 对照）
- 具体实施例的细节（参数、设备、流程、数据）
- 附图清单

**缺口没补上就不要动笔。** 先去问用户——例如「交底材料里说采样周期是 5s，
另处写 10s，以哪个为准」。带着不确定写出来的交底书，到 `06` 会全部爆出来。

### 第 2 步：按结构撰写

交底书的结构**刻意与申请文件对齐**，这样 `06` 可以逐节往下搬；
但多出第九、十两节，承载交底书特有的自由度。

```markdown
# <案件名> 技术交底书

## 一、基本信息

- 案件名：
- 建议类型：发明 / 实用新型 / 外观设计
- 申请人：                     （不知道就留空，不要编）
- 发明人：
- 交底书版本：<YYYY-MM-DD>

## 二、技术领域

一句话写清所属或直接应用的技术领域。

## 三、背景技术与现有技术的不足

客观陈述现有技术怎么做的，**指出现有技术的具体缺陷**。
不要贬低他人产品；写「现有方案存在 X 问题」而不是「某公司的产品很烂」。

## 四、要解决的技术问题

针对第三节的缺陷，本方案要解决什么。要与后文的技术方案对应。

## 五、技术方案（**最重要**）

必须详细到「本领域技术人员能够实现」的程度。至少包含：

- 整体流程或结构
- 关键步骤/部件及其作用
- 关键参数及其取值范围、为什么取这个范围
- 公式（用 LaTeX，体例见下）

> 只写「采用智能算法优化」这种话等于没写。审查指南对「公开不充分」的
> 审查就卡在这里。

## 六、有益效果

逐条对应第四节的技术问题，说明本方案带来的效果。
效果要有依据（对比实验、原理推导、量化数据），不要写「显著提升」了事。

## 七、附图清单

逐幅写明**要画什么**，并给出标号表：

| 图号 | 内容 | 关键标号 |
| --- | --- | --- |
| 图1 | 系统总体结构示意图 | 1-主控；2-传感器；3-阀门 |
| 图2 | 控制流程图 | S1~S5 |

**本 Skill 目前不生成附图**（mermaid 出图在 P3）。请用户按本清单提供
图片文件，或在申请文件里保留图号位置后续补图。

## 八、具体实施例

**说明书最重要的部分。** 至少给一个完整实施例，并尽量给出多个
（支撑上位概括，否则权利要求容易被限缩到实施例的具体形态）。

实施例里要有：具体设备型号或参数、具体操作步骤、具体数据。

## 九、备选方案与保留意见

这一节是交底书特有的，**不要删**：

- 还没想清楚的地方：「阈值目前靠试凑，理论上应该与管径有关，待验证」
- 可替代的实现：「也可以用超声波方案，但成本高，暂未采用」
- 已知的局限：「在低流速下精度下降」

这些内容让代理师理解方案的边界，也有助于后续答复审查意见。

## 十、需要用户确认的问题

编号列出。**这是交付时最需要用户回应的一节。**
```

### 第 3 步：公式体例

若交底书含公式，统一按这套来：

- 维度用**正体下标**：`b_{i,\mathrm{cpu}}`。不要写成 `b^{cpu}`——
  上标位置易被误读为幂
- **禁止同一字母多处多义**（`T` 不能既表示温度又表示周期）
- 行内与块级公式的 LaTeX 分隔符**全文统一**（建议 `$...$` 与 `$$...$$`）
- 块级公式尽量单行，便于后续转 OMML（见 `docs/refactor-plan.md` 的 D4 结论）

> ⚠ 如果素材来自 `02` 扫描出的 Word 文档，公式已经被转成退化的占位文本
> （`⟪公式N: …⟫`）。**在拿到用户提供的原式之前，不要凭占位写公式。**

### 第 4 步：脱敏（交付给外部代理师前）

交底书常含不宜外传的内容。按这四类处理：

| 类型 | 做法 | 例 |
| --- | --- | --- |
| 业务信息 | 抽象化 | 「用于某银行核心系统」→「用于大规模交易场景」 |
| 分类信息 | 用代号 | 客户名 → `A` / `B` / `C` |
| 数值信息 | 改为区间或规模 | 「日处理 1200 万笔」→「日处理量达一定规模」 |
| 公司/产品名 | 删除或中性表述 | 「由 XX 公司提供的传感器」→「温度传感器」 |

**注意：脱敏不能改变技术事实。** 「1200 万笔」可以改成「千万级」，
但不能改成「百万级」——那是在歪曲方案。

### 第 5 步：落盘（命名与不覆盖）

```
outputs/disclosure/<案件名>_<YYYYMMDD-HHMMSS>.md
```

- **时间戳命名**：每次生成都是新文件。
- **绝不覆盖旧稿。** 旧稿是用户的资产。用户说「覆盖」时，先确认一次；
  真覆盖前也把旧稿重命名保留。
- 时间戳用 `date +%Y%m%d-%H%M%S` 取，**不要自己推**。

**关于 `.docx`**：本 Skill 当前只渲染**法定申请文件格式**（`06` 的产物）。
交底书是内部材料、格式自由，目前**只产出 Markdown**。
需要 Word 版本时，如实告诉用户「交底书暂不支持导出 .docx，可等 `06` 阶段
产出正式申请文件」，不要承诺做不到的事。

### 第 6 步：交付前自查

| 检查 | 怎么查 |
| --- | --- |
| 残留占位符 | 搜「待补充」「XXX」「TODO」「？」——**零容忍**，除非是第九节刻意标注的未决项 |
| 公式有退化占位 | 搜 `⟪公式`——出现就说明还没拿到原式 |
| 附图清单与实际引用一致 | 正文提到「图3」，第七节就必须有图3 |
| 章节齐全 | 一到十节都在，**第九、十节不能省** |
| 同一字母多义 | 逐个字母过一遍 |
| 脱敏（如需要） | 按第 4 步的四类核 |

## 明确不要做

- **不要把「待补充」带进交付。** 未决项要写进第九节并说清楚，不是留空。
- **不要凭扫描出的公式占位写公式。**
- **不要覆盖旧稿。**
- **不要在信息缺口未确认时推进到 `06`。**
- **不要承诺导出 .docx**（见第 5 步）。
- **不要为了「好看」把交底书写成正式申请文件**——那样会掩盖掉本该暴露的不确定项。

## 交付

以「**交付后请确认**」收尾：

- 交底书路径、建议的专利类型；
- 第九节的未决事项（需要用户决策）；
- 第十节的问题清单（需要用户回答）；
- 附图清单（需要用户提供图片）；
- 下一步：进入 `06` 撰写申请文件。
